# Admin 主密码与共享 Main Key

状态：已实现，2026-10-29。此方案取代此前“独立认证密钥环”的候选设计。认证和主机配置使用同一 Repository、同一密钥环及同一 Main Key。

关联：[配置加密](config-encryption.md)、[认证与签发](auth-issuance.md)、[stdio/daemon 协商](stdio-daemon-negotiation.md)。[简易 MCP token](mcp-static-tokens.md) 已实现，OAuth 仍未实现。

## 1. 唯一主密码的含义

用户只需设置 Admin 主密码。密码不是 Main Key 的原始字节；现有 Argon2id 根据密码、随机 salt 和受限成本参数直接派生 Main Key，密钥环 verifier 负责密码认证。没有另存明文 Admin 密码，也没有建立第二个认证密钥环。

Main Key 只封装各对象独立随机 DEK；配置正文、认证正文仍由 DEK 通过 XChaCha20-Poly1305 加密。JWT 签名密钥继续独立随机生成，并作为认证密文的一部分保存，不能拿 Main Key 直接签 JWT。

系统秘密存储与 ENV Provider 是这同一体系中可选的自动解锁层。自动解锁只恢复密钥，不等于 Admin 登录；新登录始终需要密码派生密钥环的验证，并核对解密后的用户名。

## 2. 存储布局与提交点

| 路径 | 内容 |
| --- | --- |
| `auth.json` | 只有格式版本的公开标记，不含账号、密码、签名密钥或会话秘密 |
| `auth.enc` | 独立 authentication 类型的信封对象：Admin 身份、随机 JWT 密钥、角色权限和修订，以及 Agent 身份、权限组、绑定与 MCP token 摘要（认证状态 version=3）；旧 sessions 字段保存为空对象，活跃浏览器会话及 CSRF 不落盘 |
| `keys/config.keys` | 唯一密钥环，保存 KDF 参数、校验信息及可选的自动解锁槽位，不保存明文密码/Main Key |
| `keys/config.initializing` | 首次密钥环初始化期间的临时 Store ID 标记，用于识别允许恢复的未完成初始化 |
| `ssh_configs/…` | 沿用现有主机存储格式；认证启用不会自动转换已有明文主机，也不打开新主机加密开关 |

所有路径相对于 data-dir，默认 `.termcp`，HTTP 与 daemon 共用。认证对象采用新的对象 kind 与固定用途身份，不能被当作 profile/catalog 读取；每次保存使用新的正文代际和 DEK。

`auth.enc` 的原子发布是认证提交点。即使 `auth.json` 丢失或尚未清理，已有认证密文也阻止再次初始化 Admin。标记清理失败可以在后续解锁时重试；不能退回旧明文数据。新版标记存在但认证密文缺失时拒绝启动。

## 3. 首次设置与迁移

- 新实例：设置 Admin 账号和主密码，在同一密码派生密钥环中创建认证对象。默认不创建自动解锁槽位；用户可选择“在此设备支持时允许自动解锁”。该选项请求保存或重绑自动解锁方式，未勾选不会删除已有配置仓库的自动解锁槽位。
- 已有加密主机但尚无 Admin：若原加密密码与新主密码相同，可直接验证后复用；不同时必须提供原配置密码，验证后通过现有改密码流程统一 Main Key，再创建账号。不能丢弃既有密钥或主机数据。
- 旧明文 Admin：登录时验证旧账号密码；如果配置加密密码不同，额外输入原配置密码。迁移保留主体 ID、Instance ID、角色权限和修订，生成新 JWT 签名密钥并撤销旧会话。
- 迁移后的 Admin 记录不再含 password 字段；旧 `auth.json` 原子替换为最小标记，不生成新的明文备份。已复制的旧文件和历史备份不属于原子替换可擦除的范围。

密钥环首次创建若在写完 keys 后、catalog 提交前中断，只有匹配的 `config.initializing` 标记和正确密码才允许续建空 catalog。既有仓库丢失 catalog 且没有该标记时拒绝重建，不能把数据损坏当成首次启用。

## 4. 启动、登录和自动解锁

有有效 Provider 时，启动恢复同一 Main Key 并验证认证对象，但管理员浏览器会话不跨重启恢复。JWT 绑定本次 OpenManaged 的内存 web_boot_id，并要求存在于运行期会话表。无 Provider 或 Provider 失效时，保留初始化状态并进入待解锁，只开放最小登录/文档入口；输入主密码后一次完成解锁和登录。

待解锁时 Cookie 本身不能代替密码。正确主密码解锁后仅发放本次运行的新登录；历史会话不会重新进入运行期表。MCP 身份、权限及凭据不因浏览器登录失效而清空。stdio daemon 在需要设置/解锁时提供有界的初始化宽限，不读取 MCP stdin 中的密码。

登录时可选择为当前设备重新保存自动解锁能力。容器使用现有显式 `TERMCP_CONFIG_KEK` Provider，不引入第二份认证 KEK。Provider 不可用时保留密码解锁路径，不回退明文，也不生成替代 Main Key。

登录入口继续限制并发；认证、Store、Repository 各自使用独立密码操作门串行化密钥变更，Argon2 派生及 Provider 包装阶段释放普通业务锁。提交前复核 keyring 文件快照与关闭状态，登录完成后读取最新认证状态，保留并发权限更新。本次没有改变 KDF 参数、密文格式和重封流程；发布/重封的必要临界区仍由仓库锁保护。

## 5. 统一修改主密码

账号页 `POST /auth/password` 与原配置加密页面的改密码入口，在 managed 模式中调用同一操作：

1. 验证当前主密码与新密码确认/长度约束。
2. 先清空本次运行的登录会话并取消相关请求，再开始改密，避免中断后旧会话仍可管理实例。
3. 由现有密码变更机制派生新 Main Key，发布包含上一 Main Key 过渡封装的密钥环。
4. 对认证对象、配置 catalog 与所有活动主机对象重封 DEK；正文无需仅因 Main Key 改变而全部重加密。
5. 验证并退役旧 Main Key、更新自动解锁槽位，用户使用新密码重新登录。

若过渡发布后中断，启动仍识别双密钥状态。使用新密码登录会先继续现有重封流程，再写入新的登录会话。旧密码不再能完成登录；若在过渡发布之前失败，则仍用当前密码重试。不要仅修改账号 JSON 字段。

普通主密码变更不把 JWT 签名密钥改成派生密钥；会话失效由已持久撤销的 SID 保证。旧明文迁移则专门轮换 JWT 密钥，淘汰可能随旧文件泄露的秘密。

## 6. 实现与验证

- `configstore/authentication.go`：认证对象的独立用途、读写、密码验证与重封目标。
- `sshconfig/authentication.go`：在已有仓库上完成初始化、统一密码、登录解锁及 Provider 重绑；不持有第二套 Main Key。
- `auth/managed_storage.go`：加密状态加载、旧格式迁移、最小标记、持久会话和统一改密。
- `main.go`：将同一个 SSH 配置仓库注入认证，在 WebUI 两个改密入口之间共享操作。

验证覆盖：无明文密码/签名密钥、认证与主机共用 Main Key、Provider 自动解锁仍需密码登录、密码手动解锁、Provider 失效后的重绑、旧双密码迁移与 ID/权限保留、主机正文保持、会话撤销、认证对象不能冒充 catalog、改密中断恢复及初始化中断续建。

当前只有实例所有者 Admin 的主密码用于全局解锁。未来普通用户各自登录，Agent 使用自己的 token，不应要求它们知道部署主密码。磁盘信封保护不提供整个仓库的外部防回滚检查点，也不承诺抵御已控制解锁进程或同一 OS 身份的程序。
