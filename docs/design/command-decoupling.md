# 阶段二：用命令模式解耦调用面与能力实现

状态：实施方案，尚未修改业务源码。日期：2026-10-27。基线：`dev@76b320976ae671721f3370983f5b0d6b412685b1`。

新版代码接入说明：见基于 `dev@6a8af55` 的 [Agent 权限过滤器实施方案](agent-access-implementation.md)。其中的局部 MCP Hook 不依赖本阶段全量解耦；本页保持为旧基线的纯重构方案，不将旧调用计数和行号当作新版审计结果。

依据 [调用连接审计](capability-call-audit.md)、[714 个连接点](capability-connection-points.md) 和 [98 项语义/分支对照](capability-convergence.csv)。本阶段目标是统一执行结构，重构前后行为一致；不同时启用 [权限设计](agent-permissions.md) 中的新策略。

## 1. 本阶段完成和不完成的事项

完成：每个可对外调用的业务操作由命令对象表达；WebUI、MCP/DSL、审批恢复及相关回调通过统一执行入口调用它，调用面不再直接访问 Manager、Store、SSH、SFTP、协议客户端或 OS 文件执行函数。

“每个操作”不是每个函数调用。714 个连接点包含查询、检查、底层调用和辅助连接，不对应 714 个命令类。命令按对外可观察的业务语义划分；98 项基线对照是迁移及验收清单，也不强制一项一个对象。

不完成：新的人/Agent 权限策略、Agent 仅限 MCP 的新入口限制、补齐既有权限旁路、修复原文读取或前端旧路由问题、修改磁盘格式、调整错误文本、重命名已有 DSL 或改变生命周期。

这些问题可以保留明确后续任务，但不能夹入“只解耦”的改动。阶段二统一入口，后续阶段再在该入口明确改变授权行为。

## 2. 目标调用结构

```text
WebUI HTTP / WS              MCP / DSL
      ↓                          ↓
解析传输字段、构造命令、保留来源与 context
                  ↓
          Executor.Invoke(ctx, Command)
                  ↓
          现有检查与流程的兼容执行
                  ↓
        命令的内部执行方法（调用面不可调用）
                  ↓
       既有 Manager / Store / SSH / OS 实现
                  ↓
          返回结果 DTO 或受控数据流
                  ↓
       原 HTTP / MCP / WS 编码和错误映射
```

调用面保留协议解析与展示，不拥有能力实现。命令 Module 封装目标解析、资源访问、原有业务校验与执行；调用者与测试使用同一个执行 Interface。

只有统一入口还不够：如果调用者仍持有可直接操作的 Session、Store 或 Client，就仍然可以绕过它。完成验收需要同时收回这些直接依赖和返回值中的可执行句柄。

## 3. 模块与 Interface

建议新增一个 Go package `internal/command`，按业务族分文件；不要为了目录整齐拆出许多互相依赖的小 package。

| 文件职责 | 内容 |
| --- | --- |
| command.go | 密封的 Command 合同、执行元数据、结果类型 |
| executor.go | 唯一执行入口、内部命令执行、现有检查/日志的兼容编排 |
| runtime.go | 私有依赖集合，持有现有 Manager/Store/客户端工厂 |
| session.go、shell.go | 会话、通道、输入输出和 reader 命令 |
| file.go、profile.go | 文件和主机配置操作，保留不同入口现有语义 |
| extension.go、forward.go | 扩展和转发操作 |
| peer.go、task.go、alias.go | 直接协议路径、传输任务和运行时词汇 |
| approval.go、events.go | 审批恢复和既有事件连接的适配 |

调用方只需要知道以下合同：

| Interface / 对象 | 对调用者的含义 |
| --- | --- |
| 具体命令构造函数 | 接收强类型输入，返回 Command；不在构造时执行 IO 或隐式修改资源 |
| Command | 保存一次业务请求及描述；实际 execute 方法是 package 内部方法，调用面不能直接执行或伪造任意命令实现 |
| Executor.Invoke(ctx, Command) | 唯一执行方法，返回具体结果 DTO 或错误 |
| Result DTO | ID、快照、字节窗口、任务回执等数据，不返回可继续操作的 Session/Store/Client |
| 流式结果 | 使用声明过的 Reader/Writer/Sink 合同；底层资源及关闭/取消由命令执行器管理 |

Go 中可以用未导出的接口方法密封 Command，使同一 package 内的命令类型实现它。实现文件因此先放在同一 package；不能一边使用根 package 的私有方法密封接口，一边要求子 package 实现它。

真实业务执行方法不导出，调用面只能拿到构造后的 Command 并交给 Executor。不要提供公开的“操作 ID + 任意执行闭包”工厂，否则调用者可以声明读操作却执行写入，也没有真正解耦。

命令使用强类型参数，保留字段缺省与显式零值的区别，尤其是文件 offset 的 nil 和 0、可选 enabled、空字符串与未提供字段。输入中的 slice/map/byte buffer 需要明确复制或所有权转移，避免调用方修改已排队请求。

runtime 在 main.go 的组合根只构造一次，复用当前共享的 manager/store 实例。`internal/command` 不反向 import `internal/mcp` 或 `internal/webui`；它可以依赖现有领域 package。协议解析与 HTTP/MCP envelope 留在调用面。

## 4. 具体操作怎么变成命令

### 4.1 先封装旧路径，不重写算法

每条路径按以下顺序迁移：

1. 从基线 C 编号记录旧入口、分支、实参、检查顺序、最终执行点和结果形态。
2. 给该业务请求定义输入和输出，不把 transport request 或整个 Server/Handler 传给新命令。
3. 将原资源解析、校验和执行主体按原顺序搬入命令实现，调用相同的底层函数。
4. 将原调用点替换为命令构造与 Invoke；原响应编码和错误映射保持。
5. 两条入口的行为比对通过后，才移除迁移中的旧实现和直接字段依赖。

可以在迁移中暂时使用私有 legacy adapter，但它必须有明确移除位置；最终不能只包一层 Execute 后仍让命令回调整个 WebUI Handler 或 MCP Server。那会把耦合搬个位置，而不是解除耦合。

### 4.2 适合共享命令的情况

例如创建通道，两边已核实最终调用 `Session.CreateChildShell`。可以使用共同的 CreateShell 命令，但必须保留两边的参数解析、默认值、来源和原校验顺序；不能因为底层函数相同，就假定前置行为相同。

命令返回创建结果的数据快照，WebUI 和 MCP 各自按原方式编码。不能把 `*ChildShell` 返回给调用者，让它继续直接发送输入或读缓冲区。

### 4.3 必须保留差异的情况

| 已核实的差异 | 命令处理方式 |
| --- | --- |
| UI 原始 profile GET 返回 ReadRaw，DSL get host 走 Load 后做字段投影 | ReadProfileRaw 与 DescribeProfile 分开；阶段二不借重构改变秘密字段返回 |
| WebUI PUT profile 支持完整 TOML、改名和临时状态；MCP create/edit 分别处理字段和存在性 | PutProfileRaw 与 CreateProfileFields/UpdateProfileFields 分开，可共用私有存储 helper |
| archive 通道保留记录，DELETE 通道删除元数据 | ArchiveShell 与 DeleteShell 分开，保留现有能力映射 |
| UI internal 文件分支直接 OS，MCP internal 文件操作仍走 SFTP | 保留两种执行路径或明确的兼容模式，不强行改成同一后端 |
| UI 直接终端输入为 InputFromAPI；MCP 根据上下文可能暂存审批 | 保留输入来源、即时写入和 staging 分支，不能统一成一个默认来源 |
| 普通执行与批准后的恢复执行经过不同检查 | 统一 Invoke，但保留旧检查模式与恢复流程，阶段二不补新的复核规则 |
| UI 与 DSL 会话列表的隐藏/折叠与 namespace 过滤不同 | 保留视图语义，可共用底层查询，不强行统一返回集合 |

可以使用不同命令类型，或由服务端固定指定的兼容模式表达确实相关的变体。模式由调用适配器确定，不能接受客户端提交 bypass/approved/origin 来改变检查。

命令标识与现有 permission capability ID 不强制一对一：两个不同执行语义当前可能共用一个旧 capability。本阶段先保留映射，不顺手重命名或细化当前权限。

## 5. 现有检查和日志怎么迁移

现在的常规 MCP 路径是 `callTool → withLogging → checkAdmission → handler`；WebUI、直接 DSL 路径与审批回放并不全走这条链。阶段二不能直接把所有入口改接同一条 MCP 检查链，否则就是改变行为。

统一 Executor 内部用明确的 legacy 执行适配保留旧流程：

| 来源 | 必须保留的行为 |
| --- | --- |
| 常规 MCP 内部能力调用 | 原 admission、拒绝/待审短路、日志及 handler 的相对顺序 |
| WebUI REST/WS | 原 REST/WS Restriction 与写入行为，不新增 Agent 策略或 AI 审批 |
| 直接 DSL 查询/协议/任务/复制 | 原 namespace、refuseAction/refuseDoor 或原无检查状态；不借重构补门禁 |
| 已批准操作恢复 | 原 payload、来源、context 和恢复顺序，不重复入审或重复执行 |
| 系统生命周期清理 | 原 DEAD/关闭回调与清理时序，不按新的外部用户请求重新解释 |

检查应从“日志包装器负责调用”的耦合关系中提取，但提取后仍按旧顺序执行。未来的统一授权 Filter 挂接位置可以预留，本阶段不把此前允许的请求变成 deny/ask，也不把此前拒绝的请求变成 allow。

不能使用通用 skip_auth=true。需要恢复模式时，用受信的内部恢复调用携带既有审批计划；它仍进入同一个 Executor，但执行旧恢复语义。来源/恢复状态不能由请求正文自行设置。

## 6. 下层连接不能漏掉

调用清单不只包含用户点击按钮的路径，还包括以下连接：

- DSL ps/info 等直接读取 manager 的查询，也需要查询命令，不留一个“读接口可以直接调用”的豁免。
- peer、采样转发、帧日志、alias、task 和管道复制，不能因为不走 handlerFor 就漏迁。
- WebUI 的本机 OS 文件分支，应搬入命令实现，而不是继续留在 UI handler。
- 审批恢复、输入暂存提交和被保存的执行计划都要经统一入口，且保持单次执行。
- DEAD hook、onChange 和 UI 通知须使用清楚的内部事件合同或系统命令；调用面不再借回调持有业务对象。
- 流式读写和后台任务的关闭、取消、排空、字节顺序仍由原执行路径保证。

不把后端内部每个 Get、锁操作、buffer 操作都再包装成命令。命令 Module 内部允许直接使用既有领域实现；需要收口的是调用面到能力实现的连接，而不是业务层内部调用图。

## 7. 行为逐项比对

### 7.1 把现状作为基线

为 98 项对照保留迁移台账，至少包含 C 编号、旧路径、拟议命令、原能力 ID、原检查、观察项目、对照用例、迁移状态与旁路是否移除。未公开的旧 handler 不因重构自动公开。

为每个实际分支先补足特征测试，冻结旧行为后再移动。测试应使用公开入口/命令 Interface 和可控资源，不能只直接调用新命令内部方法后宣称入口已等价。

### 7.2 比对内容

| 层面 | 必须比对 |
| --- | --- |
| 传输 | HTTP 状态、稳定响应头、JSON 字段/类型/缺省、MCP isError/envelope、WS 帧形态 |
| 错误 | 错误码、文本、拒绝与找不到等错误发生顺序，不统一“修正”为一种错误 |
| 参数 | 默认值、nil/0、空值/未提供、编码、窗口、source、namespace 与 context |
| 副作用 | 文件内容与追加/截断模式、会话/通道记录、转发、任务和配置写入 |
| 审批 | 是否进入队列、暂存字节、批准/拒绝/超时及单次执行 |
| 生命周期 | 取消是否传播、后台任务是否继续、输出排空、关闭顺序、reader/peer/forward 清理 |
| 事件 | onChange、审批广播、UI 通知及关键日志的内容与相对顺序 |

对 JSON 可以按协议语义比较键值；文本、终端字节和有契约含义的格式必须精确比较。时间、随机 ID、临时路径只允许按预先列出的字段规范化，同时验证引用关系，不能用“忽略整块结果”掩盖差异。

### 7.3 不用生产副作用做双跑

不要在真实主机上把同一个写入/删除/启动命令执行旧版、新版各一次。用独立的临时目录、受控 SSH 服务或 fake 依赖给旧路径与新路径提供相同输入，比较结果和调用/副作用记录；每个场景使用独立初始状态。

已知旧问题同样属于阶段二基线。例如归档导出的 session lines 路由不匹配，本阶段不修复；需要修复时另列行为变更。fixture 只用合成数据，不记录真实凭据、本机用户名或共享绝对路径。

## 8. 推荐迁移顺序

1. **底座**：增加密封 Command、Executor、私有 runtime、结果 DTO 和兼容执行元数据；暂不更换全部入口。
2. **一个完整切片**：先选 ResizeShell，在 WebUI WS/REST 与 MCP 三条路径替换调用，验证参数和事件一致，证明 Interface 可用。
3. **已确认汇合的简单操作**：会话、通道、reader、forward；每次同时迁移该操作的全部已知连接点。
4. **不同实现与敏感语义**：raw/投影读取、profile PUT/create/edit、archive/delete、internal 文件 OS/SFTP 分支，保留差异。
5. **长生命周期和直接路径**：输出流、输入暂存、审批恢复、peer、task、copy 与清理事件。
6. **收口验收**：重新提取调用图，确认调用面不再直接调用领域执行函数或 OS/协议实现，原迁移台账逐项通过。

迁移期间可以并存未迁移的旧路径，但每个切片必须清楚标记；不能因 Executor 已存在就宣称全部解耦完成。不会为一个能力保留两个生产入口作运行时随机双跑。

## 9. 完成条件

- WebUI/MCP/DSL 只构造命令、调用 Executor 并编码结果；没有未经列举的直接业务连接。
- 回放、回调和生命周期路径明确归类，不能藏一个直接 handler 执行入口。
- 结果不泄露可以绕过 Executor 的领域对象或任意执行闭包。
- 原有 98 项语义/分支和新增必要的边界场景具有明确对照结果；仅 API 声明、函数名字或编译成功不能替代行为验证。
- 三 OS 执行 `make test`（race、shuffle、600s）；生命周期/文件竞态相关切片补充适当 `make test-stress`，并检查 `no_webui` 构建。
- 不在同一改动中启用新权限默认值、修复旧旁路或改变传输/磁盘格式。

本阶段的成果是一个可统一插入过滤器的执行 Interface，以及调用面不再直接依赖实现。新的过滤规则和修复行为在后续阶段单独定义、测试和交付。
