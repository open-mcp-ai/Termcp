# 多 stdio 与单 daemon 的协商：决策及遗漏项

状态：讨论稿，未实现。日期：2026-10-27。本文记录会话中已经确认的约束，并区分补充建议与待定问题；不代表全部候选规则已经获得产品确认。

相关设计：[接入方式盘点](mcp-access-auth.md)、[身份与签发](auth-issuance.md)、[Agent 业务权限](agent-permissions.md)。本次仅修改设计，不修改现有业务实现。

## 1. 已确认的范围与优先级

| 能力或规则 | 当前决定 |
| --- | --- |
| 服务端认证 | daemon 与独立 HTTP 部署共用 `.termcp` 下的持久配置、身份、权限和撤销记录 |
| HTTP OAuth | **未来计划，当前不实现**；与 stdio OAuth 一起移出当前实施范围 |
| 简易 token | **P1**：WebUI 新增 Agent、一次返回 token、状态/撤销；用户自行填写 MCP 配置 |
| stdio token 客户端 | 与 P1 简易 token 同批：读取显式配置的 Agent token、转成 Bearer、报告失败；不刷新、不自动配对 |
| stdio OAuth 客户端 | **未来计划，当前不实现**：登录 profile、浏览器授权、凭据持久化、刷新、同 profile 并发协调 |
| 多桥身份 | 同一 Agent 可有多个独立 stdio/MCP 连接；重启一个桥不创建新 Agent，不影响其他连接 |
| 权限持久化 | Admin 配置的权限必须持久化；daemon 重启后恢复原策略和撤销状态 |
| Admin 初始化 | 用户第一次运行程序时设置；当前阶段将 Admin 配置及凭据明文持久化，后续配合加密系统 |
| 配置位置 | daemon 与 HTTP 模式都使用同一数据目录，默认 `.termcp`；保留已有 data-dir 覆盖能力 |

当前先定义 Admin 初始化、配置及权限持久化；简易 Agent token 按 P1 交付，OAuth 全部留到未来。在 P1 交付前，新 managed Agent 接入仍需标为未完成，不能复用人的凭据或自动关闭认证。现有旧共享认证模式只通过显式旧模式保留，不能请求失败后自动退回。

## 2. 持久状态和连接状态必须分开

| 状态 | 保存位置/寿命 | 重启行为 |
| --- | --- | --- |
| Instance ID | 服务端持久状态；用于识别同一个部署 | 正常重启保持；不能只按端口判断是原实例 |
| Principal、Grant、Credential verifier | 服务端持久认证库 | 正常重启恢复；过期、禁用、撤销状态继续生效 |
| Admin 账号、凭据和角色 | 默认 `.termcp` 下的明文持久配置；后续接加密 | 首次设置，正常重启直接加载，不重新初始化 |
| 共享业务策略、主机范围 | 同一数据目录下的持久配置 | 完整加载后才接受业务；读取失败不回退全权 |
| daemon 启动设置 | 同一 `.termcp` 配置及现有启动参数 | HTTP/daemon 模式读取同一持久设置；新桥不得覆盖 Admin 权限 |
| Boot ID | 每次 daemon 进程启动生成的运行标识 | 改变，帮助识别旧连接状态已不可沿用 |
| Bridge connection ID、MCP session | 每个桥/每次初始化 | 重建；不充当 Agent 身份，不充当授权凭据 |
| 终端/任务运行状态与历史 | 由原业务生命周期负责 | 不能仅凭认证恢复就宣称进程或任务已恢复执行 |

Instance/Boot ID 只是识别和一致性检查信息，不是服务器身份的密码学证明。目标实例仍须符合部署连接与认证规则；公开文档或自报 metadata 不能单独证明服务可信。

权限保存应是一次可确认的持久更新：保存失败则报告失败；成功后运行时与重启后读取同一修订。共享策略变化应在新操作和待审批回放前复核，不应要求断开全部连接才能生效。

## 3. 必须补齐的 Interface 约定

### 3.1 发现、就绪与认证顺序

现有方案把“先协商认证要求”和“bridge-context 要求已认证”混在一起。建议拆为：

1. 连接配置指定的 endpoint，判断在线状态；未认证时只使用受限的公开发现信息或明确的认证错误。
2. P1 桥读取自己显式配置的 Agent token；缺失即提示配置，不代替宿主启动 OAuth 登录。
3. 验证凭据后读取 bridge-context：实例、Boot ID、协议能力、空闲参数和自身授权信息。
4. 宿主原本的 MCP initialize 经过桥转发，建立独立 transport session；桥不偷偷注入另一个 initialize。

401/403 不能等同于“服务未运行”。缺少 token、token 无效、无对应权限、目标实例不符、协议能力不兼容和服务不可达应分别报告。敏感的撤销/到期详情只展示给有权查看的 Admin，不需要通过匿名错误泄露。

### 3.2 已核验的实例复用：不新增启动互斥需求

核验结果：`internal/daemon/daemon.go:Ensure` 先探测并复用目标 host/port 上的 Termcp，只有没有服务且端口可用时才尝试启动；就绪循环也接受其他前端先启动成功的实例。MCP Start 最终使用普通 HTTP `ListenAndServe`，同一监听地址和端口不能同时由两个实例成功提供服务。

这支持本轮“多个 stdio 复用同一 endpoint”的使用方式，因此移除此前建议新增的启动锁、数据目录独占锁及跨进程实例调度，不作为认证实施前置条件。

准确的限制是按 endpoint 唯一，不是全机单例：配置不同 host/port 可以启动其他实例；两个前端并发冷启动仍可能短暂拉起多个子进程，代码通过监听和后续探测收敛，并没有显式的跨进程启动锁。当前不宣称并发启动的每个调用都必然无错误返回，也不要求为本认证方案另行改造启动机制。

依据：`internal/daemon/daemon.go:211`、`internal/daemon/spawn.go:92`、`internal/mcp/server.go:136`；依赖的 MCP HTTP Start 直接调用 `http.Server.ListenAndServe`。已运行现有 `Ensure`/`InspectEndpoint`/`PortReachable` 定向测试并通过（race 开启）；这些测试验证复用和拒绝，并未模拟并发冷启动。

stdio Interface 应尽量只暴露连接目标和自己的凭据。`no-internal`、认证模式、全局权限、退出策略等设置由 daemon 管理；新桥不能借启动参数覆盖 Admin 已保存的配置。

### 3.3 身份、连接与消息路由

认证得到 Principal/Grant 后再绑定桥连接。每个桥各自持有 MCP session、响应通道和通知流。不同桥上的相同 JSON-RPC ID 不应相互干扰，任何连接 ID/MCP session ID 都不能替代凭据。

建议请求上下文至少保留 Principal、Grant、Credential 和当前策略来源。既能定位“哪个 Agent”，也能区分“哪个授权/凭据失效”。来源是 stdio、loopback、namespace 或客户端自报名称，都不能升级为 Admin。

P1 不新增 OAuth profile，也不保存可刷新凭据。同一份 token 配置在多个桥中使用时，它们自然是同一身份；需要独立审计和撤销的接入由用户分别创建 Agent。

### 3.4 daemon 重启后的协议恢复

持久身份恢复与 MCP transport 恢复是两件事。daemon 的 Boot ID 改变后，旧 session ID、旧连接租约和未完成请求不能自动沿用。

建议初版先采用清楚的失败语义：桥发现已建立的上游 session 失效或 daemon 重启后，报告并结束当前桥，让宿主重新启动并发送 initialize。`daemon stdio` 可在新桥启动时重新 Ensure；不在一个仍被宿主视为已初始化的流里暗中重做握手。

透明重连、session 恢复及事件补发可以以后增加。新增之前，文档中的“自动恢复”只指新连接可复用原身份，不承诺正在运行的 MCP 会话或终端任务无缝继续。

### 3.5 请求结果不明时不能自动重放

断线可能发生在服务已经执行、但回复尚未到达宿主之后。对于输入、按键、命令执行、文件写入/删除等操作，桥不能只因为没收到回复就自动重发。

初版建议返回“结果未知，需要检查实际状态”，且不自动重放任何已发送的 MCP 业务请求。JSON-RPC ID 的配对功能不等于业务幂等。将来如需重试，须按业务动作提供去重/状态查询；不能用连接层统一重试冒充恰好执行一次。

## 4. 多桥存活、撤销与资源的遗漏

| 场景 | 补充建议 |
| --- | --- |
| 一个桥离开，其他桥在线 | 只清理该桥；启动过 daemon 不代表拥有停止整个 daemon 的权利 |
| 桥崩溃/网络半断 | 使用连接关闭检测和有界超时回收；不只依赖客户端主动发送 detach，也不只维护不可过期的计数 |
| 所有桥离开 | 按 daemon 自己的退出策略计时；手动常驻实例不受后来 stdio 修改 |
| 未初始化/未认证客户端 | 初始化宽限单独有界；匿名访问不能永久保活 |
| 已认证的 presence 心跳 | 可以表示进程存活，但不能延长凭据或授权期限 |
| 撤销一枚静态 token | 该凭据的所有连接失效；同一 Agent 的其他有效凭据仍可使用 |
| 撤销一个 Grant | 该授权下所有凭据/连接失效，包括多个桥 |
| 禁用整个 Agent | 该 Principal 的全部授权与连接失效 |
| 权限被收紧，待审批操作稍后获准 | 以原 Agent 和当前策略重新检查，审批不能绕过新权限 |
| 已经开始的长任务/外部写入 | 不承诺撤销会回滚；后续受限步骤如何停止按动作能力明确规定 |

还有两个待产品确认的问题，不能从“支持多个连接”自动推导答案：

1. **资源视图**：不同 Agent 默认共享哪些终端/资源？既有首版权限方案仍是共享业务策略和主机范围，不能声称已经具备每 Agent 资源隔离；namespace 不能由桥自报后充当授权。
2. **后台工作与退出**：所有连接离开但还有后台任务时，什么任务必须持有存活租约，什么任务允许随 daemon 退出？终端共享时的并发写入规则也由业务能力负责，不由 OAuth 或连接身份自动解决。

## 5. 部署、初始化和迁移尚需明确的事项

- 第一次运行程序时由用户设置 Admin；配置及凭据当前明文保存到默认 `.termcp` 下，未来再接加密。完成设置后正常启动直接读取，不反复创建 Admin；stdio 的 MCP stdin 不用于读取管理员密码。
- 本机 npx、远端部署和容器需要明确不同的初始化入口；本机浏览器不等于 MCP 宿主在本机，反向代理路径/HTTPS 不应在配置生成时丢失。
- OAuth 的 HTTP 授权服务、发现、PKCE、issuer/resource、桥登录及刷新均为未来计划，不作为当前交付条件。
- 有效权限、撤销记录与认证库加载完成后才报告可服务；存储损坏、丢失、schema 不兼容不能被当作普通“未初始化”自动重建 Admin。
- Admin 忘记密码或认证库恢复须走显式本机恢复程序；普通桥无权触发。备份恢复若回退了已撤销状态，应通过恢复流程轮换部署认证 epoch/相关凭据，不能把旧备份当成安全状态的自然延续。
- 旧共享 token/hash 不能在新模式中继续当全权旁路；升级时应提示受影响的桥，由用户选择保留显式旧模式或完成新配置。业务历史可以保留，认证身份不能静默重分配。

以上条目需要实施细化，不要求为本轮设计追加 OAuth bridge、凭据中心、多租户或每 Agent ACL。先把恢复和失败规则说清楚，再决定增加哪些能力。

## 6. 后续验收场景

1. 沿用现有 Ensure 的目标 endpoint 复用与占用端口拒绝；当前认证方案不新增 daemon 启动锁或全机单例要求。
2. 同 Agent 两个桥连接，重启其中之一后身份不变，另一个继续工作。
3. Admin 保存策略并确认成功，daemon 重启后恢复同一修订；损坏配置时拒绝业务。
4. 分别撤销 Credential、Grant、Principal，失效范围符合上表，其他有效接入不被误伤。
5. 服务执行写操作后回复丢失，桥报告结果未知，不自动执行第二次。
6. daemon 重启后宿主重新 initialize；旧 session 不越过认证或被当作新实例的有效状态。
7. 所有桥离线、桥崩溃、失效凭据不断心跳、后台任务仍在运行时，退出行为分别可解释。
8. P1 之前明确报告新 Agent 接入未完成；P1 之后验证 HTTP header 与 stdio env 共用同一个 Agent 凭据及权限模型。HTTP/stdio OAuth 都不在本轮验收范围。
